# راهنمای DNA

در این سازمان یک لایه‌ی DNA این‌گونه ساخته می‌شود. یک لایه (layer) یک بسته‌ی
معمولی است که پوشه‌ی `dna/` آن منبعِ دست‌نویس است؛ موتور (engine) آن را با
لایه‌های زیرین ادغام می‌کند و نتیجه را در مخزنِ مصرف‌کننده نمونه‌سازی
(instantiate) می‌کند.

## ساختن یک لایه <a id="start-a-layer"></a>

```bash
mkdir dna_<topic> && cd dna_<topic>
gg dna init
```

`gg dna init` فایل `dna/_dna.json` و آزمونی را که موتور را اجرا می‌کند قرار
می‌دهد. `"isLayer": true` را به آن اضافه کنید تا آزمون، تگ‌های بخش‌ها را
بررسی کند (ببینید [امکان تطبیق برای مصرف‌کنندگان](#let-consumers-adapt-it)).
بقیه را خودتان می‌نویسید.

یک لایه‌ی موضوعیِ جدید هیچ والدی (parent) اعلام نمی‌کند، به دو دلیل.
`dna_ggdna` همه‌ی لایه‌های موضوعی را فهرست می‌کند، پس لایه‌ای که لایه‌ی
چتری (umbrella) را دوباره دربر بگیرد یک چرخه می‌سازد و موتور آن را رد
می‌کند. همچنین والدهای یک لایه به همه‌ی مصرف‌کنندگان آن لایه می‌رسند — یک
والد در این‌جا محتوای خود را به همه‌ی مخزن‌های پایین‌دستی تحمیل می‌کند، چه آن
مخزن این موضوع را خواسته باشد چه نه. موضوع را مستقل (orthogonal) نگه دارید؛
ترکیب کردن کارِ لایه‌ی چتری است.

مخزنی که خودش لایه‌ی موضوعی نیست، کل مجموعه را یک‌جا دریافت می‌کند:

```bash
gg dna add dna_ggdna
```

## چیدمان `dna/` <a id="lay-out-dna"></a>

`dna/` ریشه‌ی مخزنِ مصرف‌کننده را بازتاب می‌دهد — آنچه در `dna/x/y` قرار دارد
در `x/y` نمونه‌سازی می‌شود:

| در لایه                            | نمونه‌سازی در                  |
| ---------------------------------- | ------------------------------ |
| `dna/LICENSE`                      | `LICENSE`                      |
| `dna/doc/en/guides/x-guide.md`     | `doc/en/guides/x-guide.md`     |
| `dna/dot-vscode/settings.json`     | `.vscode/settings.json`        |
| `dna/dot-claude/skills/x/SKILL.md` | `.claude/skills/x/SKILL.md`    |
| `dna/CLAUDE.md`                    | بلوکِ مدیریت‌شده‌ی `CLAUDE.md` |
| `dna/_vars.json`                   | — خصوصی، داخل می‌ماند          |

نقطه‌ی ابتدایی به صورت `dot-` نوشته می‌شود، چون انتشار در pub هر مسیری را که
با نقطه شروع شود حذف می‌کند. هر بخش از مسیر که با `_` شروع شود خصوصی است و
هرگز نمونه‌سازی نمی‌شود.

## اعلام آنچه به ارث می‌برد <a id="declare-what-it-inherits"></a>

`dna/_dna.json` تنها جایی است که پیکربندی DNA در آن قرار دارد:

```jsonc
{
  "version": 1,
  // Application order — later layers win.
  "layers": ["dna_readme", "dna_guides"],
}
```

لایه‌ای بدون والد `"layers": []` را اعلام می‌کند. تا جای ممکن یک لایه‌ی
موضوعی را مستقل نگه دارید: ترکیب در لایه‌های چتری انجام می‌شود.

## نام‌گذاری متغیرها <a id="name-the-variables"></a>

هر متغیر با `dna` شروع می‌شود و به صورت متن خام، در هر نوع فایلی، جایگزین
می‌شود. مقادیر پیش‌فرض را در `dna/_vars.json` اعلام کنید و بگذارید مصرف‌کننده
آن‌ها را بازنویسی کند:

```json
{ "ggdna": "ggdna" }
```

چون جایگزینی متنی است، یک متغیر درون یک رشته‌ی JSON یا یک بلوک کد هم کار
می‌کند — `ggdna` در یک فایل تنظیمات همان‌طور جایگزین می‌شود که در متن.

## امکان تطبیق برای مصرف‌کنندگان <a id="let-consumers-adapt-it"></a>

- فایلی با همان مسیر در لایه‌ای بعدی، فایل شما را به‌طور کامل جایگزین می‌کند
- `dna/CLAUDE.md` استثناست: هر لایه فایل خودش را به ترتیب لایه‌ها به بلوکِ
  مدیریت‌شده‌ی `CLAUDE.md` پروژه اضافه می‌کند. فقط آنچه موضوعِ شما به هوش
  مصنوعی می‌گوید بنویسید؛ هرگز متن لایه‌ی دیگری را تکرار نکنید
- `X.overrides.json` فیلد به فیلد ادغام می‌شود: اشیا به‌صورت عمیق ادغام
  می‌شوند، `"key!"` بدون ادغام جایگزین می‌کند، `"key+"` به یک آرایه اضافه
  می‌کند، `"key": null` حذف می‌کند
- `X.overrides.md` فقط بخش‌هایی را جایگزین می‌کند که یک فایل markdown با
  `## @tag Title` علامت‌گذاری کرده است
- فایل‌های ignore (`dot-pubignore`، `dot-gitignore`، `dot-npmignore`،
  `dot-prettierignore`، …) به هم پیوسته می‌شوند: فقط مسیرهایی را فهرست کنید
  که لایه‌ی شما ارائه می‌کند؛ پروژه خطوط همه‌ی لایه‌ها را دریافت می‌کند
  (ببینید [فایل‌های ignore](#ignore-files))

هر بخش از markdown خود را — راهنماها، قالب‌ها، مهارت‌ها (skills) و
`CLAUDE.md` به یک اندازه — با `## @tag Title` تگ بزنید؛ فقط عنوانِ `#` در
بالای فایل بدون تگ می‌ماند. اینکه سازمان دیگری کدام بخش را می‌خواهد تغییر
دهد قابل حدس نیست، و تگ است که یک لایه را به جای فورک‌پذیر، قابل استفاده‌ی
دوباره می‌کند. تگ را کوتاه و پایدار نگه دارید: یک یا دو کلمه که موضوع را
نام می‌برد (`@setup`، `@naming`)، یکتا در فایل و یکسان در ترجمه‌های فایل.
`"isLayer": true` را در `dna/_dna.json` تنظیم کنید تا آزمونِ قرارداده‌شده
برای هر بخش بدون تگ شکست بخورد.

## فایل‌های ignore <a id="ignore-files"></a>

فایلی که نامش با نقطه شروع و با `ignore` تمام می‌شود هرگز توسط لایه‌ی بعدی
جایگزین نمی‌شود: Helix خطوط همه‌ی لایه‌ها را در یک فایل به هم می‌پیوندد، یک
بخش `# <layer>` برای هر لایه به ترتیب لایه‌ها، و `dna/` خودِ مخزن در آخر.
الگویی که بخشی قبلی از پیش دارد، حذف می‌شود.

`dna/dot-pubignore` از لایه‌ی `dna_readme` و از لایه‌ی `dna_scripts` که پس از
آن فهرست شده است:

```gitignore
/doc/*/guides/
/doc/*/templates/
/scripts/
```

```gitignore
/doc/*/guides/
/scripts/
```

فایل `.pubignore` پروژه:

```gitignore
# .gitignore
.dart_tool/
coverage

# dna_readme
/doc/*/guides/
/doc/*/templates/
/scripts/
```

`dna_scripts` چیز تازه‌ای اضافه نمی‌کند، پس بخشی نمی‌گیرد.

یک `.pubignore` در ریشه با `.gitignore` پروژه شروع می‌شود: `dart pub
publish` به جای `.gitignore` فایل `.pubignore` را می‌خواند، پس بدون آن هر
چیزی که git نادیده می‌گیرد منتشر می‌شد. هرگز `/dna/` را فهرست نکنید — بسته‌ای
که به عنوان لایه استفاده می‌شود از پوشه‌ی منتشرشده‌ی `dna/` آن خوانده می‌شود.

## ارسال به هر دو رجیستری <a id="ship-it-to-both-registries"></a>

یک لایه هم از Dart و هم از TypeScript مصرف می‌شود، پس از همان مخزن دو بار
منتشر می‌شود:

- `pubspec.yaml` — `name: dna_<topic>`، منتشرشده در pub.dev
- `package.json` — `name: @<scope>/dna-<topic>`، منتشرشده در npm
- `files: ["dna", "README.md", "LICENSE"]` — بسته‌ی tarball پوشه‌ی منبع را
  حمل می‌کند، نه چیزی ساخته‌شده

هر دو نسخه را هم‌گام نگه دارید: موتور وقتی دو نسخه‌ی یک لایه با هم فرق داشته
باشند هشدار می‌دهد و نسخه‌ی npm را به کار می‌برد.

## بررسی <a id="verify-it"></a>

آزمونِ قرارداده‌شده در هر اجرا لایه را در مخزن خودش نمونه‌سازی می‌کند، پس لایه
همیشه توسط مخزنی که آن را ارائه می‌کند آزموده می‌شود:

```bash
dart test      # or: pnpm test
gg dna build   # the same run, without a test framework
```

پیش از اجرایی که می‌نویسد commit کنید: هر فایل موجودی که موتور بازنویسی
می‌کند باید commit شده باشد تا هر بازنویسی از طریق git قابل بازیابی بماند.
